# Sensor Report — обработка данных датчиков

## 1. Описание проекта

Компания использует температурные датчики двух производителей.
Устройства отправляют JSON-записи с разными названиями полей.
Сотрудникам нужна программа, которая приводит данные к общему формату,
отбрасывает ошибочные записи, сохраняет показания в SQLite и создаёт CSV-отчёт.

Все данные в проекте искусственные. Температура измеряется в градусах Цельсия.

Твоя задача — самостоятельно разработать такую программу на Python.

## 2. Что ты освоишь

- Python: функции, словари, списки, циклы, модули и исключения.
- Чтение JSON и проверку входных данных.
- SQLite и SQL: создание таблиц, INSERT, SELECT, JOIN, GROUP BY.
- pandas: чтение результатов SQL и экспорт таблицы.
- pytest: проверку функций и всей обработки на небольшом примере.
- Docker: сборку образа и запуск программы в контейнере.
- Git: небольшие осмысленные коммиты.
- Работу с ИИ-агентом и проверку предложенного им кода.

Внешний сервер, сайт и машинное обучение в этом проекте не нужны.

## 3. Исходные файлы

- data/devices.json — справочник устройств.
- data/readings.json — показания в двух форматах, включая ошибки.

Исходные файлы нельзя исправлять, чтобы программа проходила проверку.
Ошибочные записи добавлены намеренно.

### Формат A

{
  "format": "A",
  "device_id": "sensor_01",
  "timestamp": "2026-10-26T09:00:00",
  "temperature": 20.0
}

### Формат B

{
  "format": "B",
  "sensor": "sensor_02",
  "measured_at": "2026-10-26T09:00:00",
  "value": 18.0
}

### Общий формат после преобразования

{
  "device_id": "sensor_01",
  "timestamp": "2026-10-26T09:00:00",
  "temperature_c": 20.0
}

Поле format в нормализованную запись не переносится.
Исходный словарь не должен изменяться.

## 4. Правила проверки

Проверяй записи в следующем порядке:

1. format должен быть A или B.
   Иначе ошибка unsupported_format.

2. Должны присутствовать все поля соответствующего формата.
   Иначе missing_field.

3. Идентификатор устройства должен быть непустой строкой.
   Иначе invalid_device_id.

4. Устройство должно существовать в devices.json.
   Иначе unknown_device.

5. Время должно быть строкой строго формата YYYY-MM-DDTHH:MM:SS
   и обозначать существующую дату и время.
   Иначе invalid_timestamp.
   Часовые пояса в этом проекте не используются.

6. Температура должна быть числом int или float, но не bool.
   Строки вроде "22.5" автоматически в числа не преобразовывать.
   Иначе invalid_temperature_type.

7. Температура должна быть конечным числом от -50 до 100 включительно.
   Иначе temperature_out_of_range.

Возвращай только первую ошибку записи.

После проверки ищи дубликаты.
Ключ дубликата — пара device_id + timestamp.
Сохраняй первую корректную запись с таким ключом.
Последующие корректные записи с тем же ключом пропускай,
даже если температура отличается.

## 5. Результаты работы

Программа создаёт в указанной выходной папке:

- readings.db — база SQLite;
- report.csv — сводка по устройствам;
- errors.json — список ошибочных записей;
- summary.json — счётчики обработки.

### errors.json

Массив объектов с полями:

- record_number — номер исходной записи, начиная с 1;
- reason — код ошибки из раздела 4;
- record — исходная запись без изменений.

Дубликаты в errors.json не включать.

### summary.json

{
  "total": 14,
  "accepted": 6,
  "rejected": 7,
  "duplicates": 1
}

Должно выполняться равенство:
total = accepted + rejected + duplicates.

### Структура SQLite

Таблица devices:

- device_id: TEXT PRIMARY KEY
- location: TEXT NOT NULL

Таблица readings:

- device_id: TEXT NOT NULL
- timestamp: TEXT NOT NULL
- temperature_c: REAL NOT NULL
- составной PRIMARY KEY (device_id, timestamp)
- FOREIGN KEY device_id REFERENCES devices(device_id)

Включи проверку внешних ключей для соединения SQLite.
Используй параметры SQL-запросов при вставке значений:
не подставляй данные в SQL через f-строки.

### report.csv

Столбцы строго в таком порядке:

device_id,location,count,avg_temperature,min_temperature,max_temperature

Сводку рассчитай SQL-запросом с JOIN и GROUP BY.
Результат загрузи в pandas и сохрани через to_csv(index=False).

Включай только устройства, у которых есть принятые показания.
Сортировка — по device_id.
Среднее округли до двух знаков после запятой.
Кодировка — UTF-8.

### Повторный запуск

Каждый запуск заново формирует результаты текущего входного файла.
Существующие таблицы очищаются в транзакции: сначала readings, потом devices.
База не должна накапливать данные предыдущих запусков.

Не удаляй всю выходную папку.
Перезаписывай только четыре файла результата проекта.

## 7. Этапы разработки

### Этап 1. Подготовка репозитория

Что сделать:

- Создай репозиторий и открой папку в VS Code.
- Сохрани TASK.md и исходные JSON-файлы.
- Создай виртуальное окружение .venv.
- Создай .gitignore.
- Добавь в README краткое описание будущей программы.

В .gitignore включи:

.venv/
__pycache__/
.pytest_cache/
*.pyc
output/
.env

Исходные JSON из data/ должны попадать в Git.

Пояснение:
Виртуальное окружение отделяет зависимости проекта.
Git хранит исходники и учебные данные, но не временные результаты.

Готово, когда:
git status не предлагает добавить .venv, а оба JSON видны в репозитории.

Коммит:
chore: initialize project and sample data

### Этап 2. Преобразование форматов

Что сделать:

- Напиши функцию normalize_record(record).
- Научи её преобразовывать A и B в общий формат.
- Не изменяй исходный словарь.
- Для неизвестного формата поднимай ValueError.

Пояснение:
Функция должна возвращать словарь через return.
Печать результата на экран не заменяет возврат значения.
На этом этапе можно считать значения корректными.

Готово, когда:
два разных входных формата дают одинаковые названия выходных полей.

Коммит:
feat: normalize two sensor formats

### Этап 3. Проверка и обработка файла

Что сделать:

- Реализуй все проверки из раздела 4.
- Прочитай справочник устройств и список показаний.
- Обработай записи по порядку.
- Раздели принятые, ошибочные и повторные записи.
- Запиши errors.json и summary.json.

Можно изменить интерфейс normalize_record, если это делает код понятнее.
Выбери единый способ передачи ошибок: исключение с кодом
или явно возвращаемый результат. Опиши свой выбор.

Пояснение:
Ошибка одной записи не должна останавливать обработку остальных.
Но отсутствующий файл или сломанный синтаксис JSON — ошибка всего запуска.
Для такой ошибки выведи понятное сообщение и заверши программу с кодом 1.
Не скрывай все исключения через except: pass.

Готово, когда:
счётчики совпадают с разделом 8.

Коммит:
feat: validate records and collect processing errors

### Этап 4. База данных

Что сделать:

- Создай SQLite-базу с двумя таблицами.
- Загрузи справочник и принятые показания.
- Используй параметры запросов и транзакцию.
- Обеспечь повторный запуск без накопления строк.

Пояснение:
SQLite хранит базу в одном файле и не требует отдельного сервера.
PRIMARY KEY запрещает повторные ключи.
Транзакция объединяет изменения: они подтверждаются вместе
или отменяются при ошибке.

Готово, когда:
в devices три строки, в readings шесть;
повторная обработка оставляет те же количества.

Коммит:
feat: store validated readings in sqlite

### Этап 5. Отчёт

Что сделать:

- Напиши SQL-запрос, объединяющий devices и readings.
- Рассчитай количество, среднее, минимум и максимум по устройствам.
- Загрузи результат запроса в pandas.
- Сохрани report.csv без индекса DataFrame.

Пояснение:
JOIN добавляет к показанию расположение устройства.
GROUP BY собирает показания одного устройства в группу.
pandas здесь отвечает за табличный результат и выгрузку.

Готово, когда:
значения CSV совпадают с разделом 8.

Коммит:
feat: export device summary report

### Этап 6. Командная строка

Ожидаемый интерфейс из корня репозитория:

python -m sensor_report --devices data/devices.json --input data/readings.json --output output

Что сделать:

- Реализуй аргументы через argparse.
- Создавай выходную папку, если её нет.
- Не привязывай код к абсолютным путям своего компьютера.
- После успешного запуска печатай краткие счётчики.
- Поддержи --help.

Пояснение:
python -m sensor_report запускает файл __main__.py пакета.
argparse превращает параметры терминала в значения для программы.

Готово, когда:
одной командой создаются все четыре результата.

Коммит:
feat: add command line interface

### Этап 7. Автоматические тесты

Обязательные проверки:

- Нормализация форматов A и B.
- Исходный словарь не изменяется.
- Неизвестный формат.
- Отсутствующее поле.
- Пустой идентификатор и неизвестное устройство.
- Несуществующая дата.
- Температура строкой и температура bool.
- Границы -50 и 100 принимаются.
- Значение вне диапазона отклоняется.
- Дубликат не добавляется повторно.
- Полный запуск на учебных данных даёт ожидаемые счётчики и отчёт.
- Повторный запуск не увеличивает число строк.
- Пустой массив показаний даёт нулевые счётчики и CSV с заголовками.

Пояснение:
Тест содержит вход, вызов проверяемого кода и assert с ожидаемым результатом.
Используй tmp_path для временной базы и файлов.
Не заставляй тесты менять настоящую папку output/.

Запуск:

python -m pytest -q

Готово, когда:
все тесты проходят и хотя бы один тест ловит специально внесённую ошибку.
После проверки ошибку обязательно исправь.

Коммит:
test: cover validation and pipeline behavior

### Этап 8. Docker

Что сделать:

- Запиши зависимости pandas и pytest в requirements.txt.
- Зафиксируй версии, на которых успешно прошли твои тесты.
- Создай Dockerfile на основе python:3.12-slim.
- Задай WORKDIR, установи зависимости, скопируй пакет.
- Настрой запуск python -m sensor_report через ENTRYPOINT.
- Добавь .dockerignore: .git, .venv, __pycache__,
  .pytest_cache и output.
- Передавай исходные данные и результаты через подключённые папки.

Пояснение:
Образ — подготовленное окружение с программой.
Контейнер — запущенный экземпляр образа.
Подключённая папка позволяет забрать результаты на компьютер
после удаления контейнера.

Сборка:

docker build -t sensor-report .

Запуск из PowerShell, находясь в корне проекта:

docker run --rm --mount "type=bind,source=$($PWD.Path)/data,target=/app/data,readonly" --mount "type=bind,source=$($PWD.Path)/output,target=/app/output" sensor-report --devices /app/data/devices.json --input /app/data/readings.json --output /app/output

Перед запуском создай output/, если её ещё нет.
Команда рассчитана на работающий Docker с Linux-контейнерами.

Готово, когда:
контейнер создаёт на компьютере те же результаты, что локальный запуск.
Проверь числовые значения и счётчики, а не только наличие файлов.

Коммит:
build: add docker execution

## 9. Как работать над проектом

- Делай этапы по порядку.
- Не пиши весь проект одним большим файлом.
- После рабочего этапа проверяй git diff, делай коммит и push.
- Не нужно заранее создавать все модули пустыми.
- Если застрял, присылай номер этапа, код и полный текст ошибки.
- Использовать документацию и ИИ можно, но каждую принятую часть кода

Это не дедлайн: на изучение новых инструментов может уйти больше времени.

## 10. Дополнительное задание — только после основной части

Создай генератор показаний:

python -m sensor_report.generate --count 100 --seed 42 --output data/generated.json

Требования:

- Использовать устройства из учебного справочника.
- Генерировать оба формата.
- Все записи корректные, ключи device_id + timestamp уникальные.
- Одинаковые count и seed дают одинаковые данные.
- Время начала фиксированное, а не текущее.
- Сгенерированный файл обрабатывается основной программой.
- Для count=100 результат: accepted=100, rejected=0, duplicates=0.

Не расширяй проект веб-интерфейсом или ML, пока основная часть не завершена.
